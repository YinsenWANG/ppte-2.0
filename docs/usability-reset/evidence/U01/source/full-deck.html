CHERRY STUDIO开放 / 使用经验也是起点

从个人体验出发

先用起来。
再说清楚。

你在使用中遇到的一个障碍，
可能就是参与的起点。

先说明自己想完成什么，再记录哪里受阻。
把“感觉不好用”转成可以讨论的具体场景，
让其他人理解问题，也让改进有据可循。

这是一种参与思路，并非官方处理时限或采纳承诺。

CHERRY STUDIO反馈 / 把体验变成可讨论的信息

让别人能重走你的路径

一份反馈，
先把问题讲清。

不用先知道修复答案。
清楚的上下文，已经能减少来回追问。

右侧为虚构写作示例，
不代表已发现的产品缺陷。

反馈写作示例 · 非真实缺陷

某个操作后，结果与预期不同

场景与步骤
我想完成什么？从哪个页面开始？
按顺序列出触发问题的操作。
预期与实际
我以为会出现什么？实际出现了什么？
补充可以帮助定位的环境与版本。
可复现的边界
每次都出现，还是偶尔发生？
如需附素材，先去除其中的私人信息。

CHERRY STUDIO协作 / 让一次修改容易理解

把改动交给共同维护

从独立分支，到一个清楚的 PR。

  1. 01

    Fork 与克隆

    建立自己的工作副本，
    先阅读贡献指南与分支策略。

  2. 02

    创建分支

    围绕一个明确的问题组织改动，
    保持范围便于解释与审阅。

  3. 03

    提交修改

    完成修改并提交、推送，
    交代做了什么以及如何验证。

  4. 04

    发起 Pull Request

    说明修改的原因，
    跟进讨论并补充必要的信息。

CHERRY STUDIO行动 / 一次小而完整的贡献

把参与变成可执行的下一步

从你最了解的那个问题开始。

下列是作者的参与建议，
具体要求以项目贡献指南为准。

你看到的机会可以做的一件事让协作者容易接手
01使用中遇到障碍把问题整理为可复现的反馈写明操作步骤、预期与实际结果
02说明不够清楚补充一段文档或一个具体例子说明适用场景，核对步骤是否可用
03交互可以更顺在设计讨论中提出改进方案带上使用场景，解释取舍与影响
04找到了修复方法在独立分支完成修改并提交 PR描述原因、改动与验证结果
先缩小范围选一个问题 → 读贡献指南 → 讨论或提交 → 跟进反馈
贡献入口依据固定 README；行动清单为作者建议，不代表官方流程承诺07 / 09
CHERRY STUDIO持续 / 提交之后，协作仍在继续

贡献不止于提交

留出空间，
接住反馈。

把讨论看作共同理解问题的过程。

信息不够时

补充复现步骤、例子或验证结果，帮助协作者缩小不确定性。

意见不同时

回到使用场景，解释取舍；必要时把大方案拆成小改动。

建议持续跟进，但不预设维护者的响应速度或合并结果。

# PPTe 重设计：让 HTML 成为作品本身

版本：HTML-first 1.0 · 2026-09-06 · 状态：设计决策已确认，尚未实现。

本方案来自用户对实际成品的六项反馈。它**替代** docs/evolution/IMPLEMENTATION_PLAN.md 的产品边界、生成架构、交付格式和发布门禁；旧文档、任务状态与审查保留为历史，不再要求远程开发继续完成旧 D07/P01/Q01/Q02 的全部范围。尤其不再做 PPTX 或 Office 验收。

当前代码基线为 `4aee9da597ceef29df30f22a65f5bafc9f2bc354`。此前审查和 Cherry 实际制作暴露的问题是新设计的输入，不意味着新设计已经解决它们。下一阶段首先交付“快速生成、好看、能保存”的完整小版本。

## 1. 六项决定

|用户反馈|新的产品决定|明确的退出条件|
|传统格式增加负担|只支持 HTML 与按需 PDF。移除 PPTX/PPT/Office 适配、导出映射、兼容矩阵与相关发布门禁|新发行包和生成调用链不包含 Office 转换依赖，不再运行 Office 验收|
|慢、耗 token|Agent 直接写 HTML/CSS，CLI 做增强和少量检查|默认生成路径没有 Presentation IR → Recipe → Transaction → Portable 的往返|
|审美差、模型能力受限|模型控制完整构图、字体层级、CSS Grid/Flex、SVG 和页面节奏；提供参考，不强套配方|相同材料、相同模型条件下，与直接 HTML 生成做盲评和耗时对照|
|交付一堆文件|默认只返回 `演示稿.html`，它同时是作品、编辑源和放映入口|用户目录默认只有一个新增文件；PDF、另存为、开发报告均由明确动作触发|
|没有保存和自动保存|保存写回当前 HTML；自动保存可落盘；缓存仅作为恢复草稿|关闭后从原路径再开，内容保留；只有落盘成功才能显示“已保存”|
|菜单像原始控件堆砌|重做一套统一编辑 UI；上下文浮动工具栏与按需属性面板|不存在常驻表单墙、白底白字、编辑工具进入观众画面|

主线仍是 **NPM + 原生 Skill**。不需要 MCP stdio、第二个模型或新模型密钥。产品名称可以保留 PPTe；`.ppte` 文件不再是新用户工作流的一部分。QuickJS、Electron、多人协作不是本阶段依赖。

## 2. 根因与此次纠偏

实际制作过程包含读大型规格、生成 IR、计划文件、预览收据、事务修复和再次交付；大量中间结构服务于工具，而不是用户的作品。固定配方限制每页槽位与容量，模型的 HTML/CSS 能力没有直接用于最终构图。首次环境安装、下载浏览器和完整字体又放大了耗时。

这是可观察的架构问题，但**目前没有受控数据支持“必然慢数十倍”这一数值**。必须记录安装冷启动与日常生成分别耗时，不能把首次安装全部归为推理性能，也不能因此忽略真实端到端体验。PPTX 是要删除的范围，但删除它本身不保证生成变快；真正关键的是去掉强制中间表示和反复转换。

此前生成的单 HTML 约 11.1 MB，其中资源约 7.8 MB，主要是完整中文字体。默认不再下载和嵌入完整字体，也不让简单文本生成依赖图像导出工具或浏览器安装。

## 3. 用户从头到尾只面对一个作品

用户说“用 Cherry Studio 开源之路做一份演示稿”。Agent 直接完成叙事和 HTML/CSS 设计。工具增强后给出一个 `Cherry Studio.html` 链接。

打开就是适应窗口的阅读画面，顶部只保留文稿名称、保存状态、“编辑”和“放映”。进入编辑才显示页缩略图、选择反馈与上下文工具。进入放映只显示当前幻灯片；控制在明确唤出、悬停或键盘聚焦时出现，闲置后退出观众画面。演讲者备注、预览、计时放在专用视图。

PDF 在“更多 → 导出 PDF”中按需生成。日常主按钮是“保存”，快捷键 Cmd/Ctrl+S；“另存为”是次级菜单项，不再承担所有保存。

诊断、安装记录、自动保存日志、测试图、原始资料和开发用草稿可以存在工作区或应用缓存，**不作为用户交付物列出来**。不自动生成 ZIP、离线编辑器副本、`.ppte`、PPTX 或 PDF。

## 4. HTML/CSS 原生创作合同

### 4.1 模型写的就是页面

模型直接输出普通 HTML/CSS：完整字体层级、渐变、网格、图片、SVG、图表和图形均可使用。不会为了套“标题 + 两段 + 图片”而重新生成一个低保真版本。

最小增强约定只包括：幻灯片容器 `data-ppte-slide`；可编辑对象的稳定 `data-ppte-id`；可选 `data-ppte-kind`、备注和来源。AI 可直接声明；缺失 ID 由工具确定性补齐。表格采用原生 table，图形采用 SVG，图片与视频采用 HTML 元素。图表优先可解释的 SVG 和少量数据元信息，无 Office 数据映射。

元数据仅存 documentId、formatVersion、saveRevision、备注／来源和编辑约束；不再次保存整套内容、几何和样式的 JSON 镜像。**浏览器布局和 DOM/CSS 才是作品的表示方式。** 禁止在新核心内部悄悄重建旧 Presentation IR 或“所有内容必过 schema 才可画”的体系。

### 4.2 一份持久内容，一套可信运行时

最终单 HTML 的载荷包括一次性的页面 HTML/CSS、内嵌资源、轻量元数据，以及构建时注入的可信编辑／放映运行时。不得同时嵌入完整 `.ppte` ZIP、Base64 版项目和另一份渲染文档。

建议持久内容放在一个 inert template 中，打开后挂载到同源但禁止内容脚本的隔离 iframe。编辑期间 iframe 中的 DOM 是活动内容；保存时从该 DOM 序列化一次，替换模板内容，滤除选区、拖拽柄、contenteditable、临时光标与工具 UI。保存同一个文件一百次不能累积旧模板、旧 runtime、object URL 或 Base64 副本。具体封装先通过 H01 的保真和体积原型，再冻结。

隔离 iframe 保留 Grid/Flex/CSS 自定义属性、渐变、SVG 和字体能力，避免生成稿 CSS 污染编辑器。作者内容默认没有任意 JS 执行能力；禁止 inline event handlers、javascript URL、外部脚本和会读写本地文件的内容行为。动画通过可信运行时和 CSS 执行，视频用原生媒体。交付时将已授权资源内嵌，默认阻止内容的外部网络请求、导航、表单提交与弹窗；通过 CSP/iframe 权限验证，而不只用字符串替换过滤。增强器应明确报告被拒绝的可执行内容，不能静默破坏版式再宣称成功。

生成文件的模板编码和嵌套 style/template 转义由程序处理，不让模型手写大段 Base64 或转义 JSON。打开普通第三方 HTML 必须先在 inert DOM 中解析，不执行它的脚本；不能因为文件名是 HTML 就给予保存服务的权限。

### 4.3 编辑能力与自由布局共存

所有文字支持内容编辑和选区格式；图片／视频可替换；表格可编辑单元格及行列；CSS 背景和常用 SVG 图形提供对应属性。对绝对定位对象提供拖动、尺寸、旋转；对 Grid/Flex 流式布局提供重排、间距、轨道／容器调整，不能把所有节点一拖就改成 absolute，破坏响应布局。

复合插画或复杂 SVG 默认作为可移动、可替换的整体，允许解锁后深入编辑。不承诺任意外部网页所有 CSS 都能通过通用控件无损修改；增强器给出能力标记和具体原因，用户仍可通过 Agent 修改 HTML/CSS。

用户编辑经同一套 DOM 编辑命令进入撤销栈。命令记录稳定节点 ID、前后局部 DOM/CSS 和基准摘要；无需重放几十种 Office 语义操作。AI 局部修改默认只操作选定节点／页，使用 expected hash 防止覆盖新的人工作业；重排整页需要保留人工保护节点，不能把整套 HTML 重生成作为改一句话的实现。

## 5. 真正保存：文件、草稿和授权分别表达

### 5.1 支持矩阵与产品选择

|入口|如何保存到原文件|自动保存承诺|
|NPM 本地编辑入口，推荐完整编辑路径|轻量本地服务绑定用户选择的 HTML，校验冲突后写回同一路径|默认开启，输入停顿约 800 ms 后保存；每次成功显示文件落盘状态|
|单 HTML + 浏览器支持且获文件写权限|首次“保存”明确选择／绑定目标文件，后续通过 File System Access 写回|授权有效时自动保存；重新打开需检查权限，必要时重新授权|
|单 HTML + 缺少文件写 API／权限|可浏览和放映；编辑前明确说明无法直接覆盖原文件，并提供本地编辑入口或显式下载保存|只能明确显示草稿暂存／尚未写入文件，不能承诺原文件自动更新|

必须承认浏览器边界：单个 `file://` HTML 不能在任意浏览器里、零授权地改写它自己的磁盘文件。新产品以 **NPM 本地编辑入口提供可靠的跨浏览器原文件自动保存**；单文件直开仍可立即浏览／放映，支持授权写入的环境还能独立编辑保存。第一次建立关联的步骤不可伪装成已经完成。

因此推荐命令为 `ppte edit ./作品.html`，打开已绑定此文件的同一套编辑界面；不生成第二个“编辑器.html”。单文件中的“在本地编辑器打开”必须走已安装服务的真实连接机制，未安装时显示简短安装／启动指导，不能假设浏览器能直接执行 shell 命令。首版不要求系统级双击文件关联或常驻服务。

### 5.2 保存协议

状态机：已保存 → 有修改 → 保存中 → 已保存；另有无文件授权、仅草稿、冲突、失败。显示“已保存”需要文件写入完成的确认，不能在发起请求或写 IndexedDB 后提前显示。

编辑命令合并写入，composition 期间不提交半个汉字。串行写队列绑定 saveRevision；旧请求迟到不能覆盖新版本。保存前比较磁盘文件摘要／版本，外部 Agent 修改或另一窗口写入时停止覆盖并展示冲突；至少提供重新读取和保留当前修改的恢复分支，不自动 last-write-wins。

本地服务采用同目录临时文件、写完校验后替换，处理磁盘满／只读／中断，保留上一个可恢复版本。缓存和恢复日志存应用数据目录，按数量／容量上限轮换，不给用户项目目录堆侧车文件。断电耐久性的承诺须用目标系统上的写入与恢复测试确定，不只凭 rename 成功宣称。

浏览器直接写入使用授权 handle 与 createWritable/close，验证当前文件内容再写，并在支持 Web Locks 的同源窗口间互斥。浏览器 API 不提供与任意外部进程共享的原子 compare-and-swap；这个并发边界必须注明，本地服务承担更强的协调能力。保存失败时保留修改，状态持续可见，Cmd/Ctrl+S 可重试。

自动草稿包含 documentId、基准文件摘要、草稿 revision 和时间；重开时只在匹配基准上自动恢复，否则提示冲突。移动／复制文件不能仅凭 documentId 把另一份草稿覆盖进去。无可靠存储、配额满、隐私模式或权限丢失时直接显示限制；关闭时警告只作补充，不能依赖 beforeunload 才开始保存。

### 5.3 本地服务的最小边界

仅绑定 loopback，用户一次只授予选定文件／目录的能力，不暴露任意路径写 API；校验 Origin、随机会话令牌和请求格式，限制请求体，阻止跨站请求和路径穿越。运行文稿的 iframe 无保存令牌、无内容脚本权限。服务保存的永远是安全序列化后的 HTML，而非文稿发来的任意路径或命令。端口稳定性、重启发现和多文稿映射属于 H02 必须实现的行为；不能把一个只存在于开发脚本中的服务器当作成品。

来源：[Chrome File System Access 文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)、[MDN showSaveFilePicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker)、[MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)、[MDN OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)。文件选择 API 存在支持范围和授权限制；file URL 的 localStorage 行为未统一定义，OPFS 也不是用户原文件。此支持矩阵是待实测合同，不是已支持声明。

## 6. 重新设计编辑界面

视觉方向：安静的中性色外壳、清晰字级、8 px 间距体系、少量分组、统一图标与状态；作品的颜色与编辑器 UI 分离。

- 顶栏：返回／文件名、保存状态；撤销重做、编辑模式、放映、更多。保存状态可点开查看原因；不摆一整排调试和 Agent 按钮。
- 左侧：缩略图、页码、添加页，默认宽度约 180–220 px，可折叠。
- 画布：保留充分留白，只在当前选择上显示细边和控制柄；缩放控件收在底部。
- 选文字：附近浮动字号、粗体、颜色、对齐等最常用项；更多设置进入精简面板。
- 选图片／形状／表格：只出现相关操作，不展示其他对象的全套字段。
- 属性面板：明确分组、色板和尺寸步进，不出现未统一样式的 select/fieldset 表单墙。
- 放映：编辑器完全退出观众视图；黑屏为真实黑幕；退出和恢复始终可由键盘完成。

原生操作系统文件选择器应保留；“不用原生控件堆界面”不等于重写系统文件对话框。UI 控件必须有键盘路径、可见焦点、可读标签和至少 4.5:1 的正文对比目标。颜色／字号混合状态、空选区、保存失败和权限过期都要在设计原型中出现。

[交互原型](UI_PROTOTYPE.html) 用于冻结层级、视觉和保存状态表达。它不是已实现编辑器，不保存真实文件，不计入产品验收。

## 7. 让模型负责设计，工具负责可靠交付

原生 Skill 的默认内容压到约 1,500 tokens 以内；按需引用参考，而不是每次读取大份 schema、整套配方和发布规格。默认看最多两个风格方向，选择一套后直接写稿，不固定生成三页代表稿、计划、收据再生成全套。

生成流程：理解材料和用途 → AI 写 HTML/CSS → 一次增强与静态检查 → 可用时一次全稿缩略图／溢出检查 → 最多一次必要修正 → 返回一个 HTML。环境安装只做一次；默认不装 Office、Python，也不下载完整字体。没有浏览器组件时仍能生成并交付 HTML，但视觉检查标记未执行，不能虚报通过。

设计引导描述构图原则和优秀例子：观点先行、明确焦点、标题层级、与内容匹配的图形、疏密节奏、合适留白、真实来源。禁止固定槽位数、机械三卡片、为了硬约束缩小正文字号，或把可编辑文字烘焙进图片。保留模型设计的 CSS，不再用通用模板覆盖。

资源默认使用系统中文字体栈和原创轻量 SVG；确有需求时才嵌入许可明确的图片、视频或字体。资源字节由程序读取，不进入模型上下文。需要缺失字形时可提示并采用已声明的系统字体回退，不应因为完整字体少一个元数据字段就阻止所有 HTML 交付。不同系统字体导致的差异须通过实际排版检查处理，不能宣称跨平台像素一致。

CLI 常规输出只给路径、页数、是否通过和少量错误 ID，默认不超过约 1 KB。详细报告写缓存文件，按需读取；不把完整 HTML、Base64、事务和文档反复回传给模型。

## 8. 速度、体积和审美的真实门槛

先测基线再优化。使用同一个模型、相同推理配置、同一份材料、页数和资源，比较“直接写 HTML”与“PPTe 增强生成”。分开记录首次安装、研究取材、模型生成、工具处理、修正、总耗时，以及输入／输出 tokens、调用次数、重试和生成失败。运行时不并发跑重测试。

首轮选择 Cherry 开源之路、产品介绍、含真实表格／数据的汇报各一份，每份各跑三对，保留全部首稿和失败，不挑最好的一份。数量足以发现明显倒退，但不声称具备大样本统计证明。超长材料和视频另设资源层级，不能与纯文本混算。

待实测冻结的初始目标：热环境总耗时中位数 ≤ 直接 HTML 基线的 1.25 倍、token 总量中位数 ≤ 1.20 倍，尾部与失败单独报告；对十二页轻资源稿，纯增强处理目标 ≤ 2 秒，不含模型、研究和浏览器渲染。不可通过减少页数、删事实、跳过必要保存验证来过线。

体积初始目标：无媒体时可信编辑／放映 runtime ≤ 250 KB gzip；不含用户媒体与可选字体的完整 HTML ≤ 1 MB。同时报告原始字节、gzip 和媒体字节；不以“压缩后小”掩盖用户实际下载尺寸。原稿资源过大应明确报告来源并提出压缩选项，不自动降低图片质量或删视频。

审美由项目负责人和两名目标使用者盲评，比较信息层级、构图、字级、节奏、图形表达和完成感。首轮九对中至少六对不逊于直接 HTML，且无人认为编辑 UI 阻碍基本使用，作为初始门槛；不是模型自己打分。任何丢事实、文字遮挡或保存丢失都是独立失败，不能被平均美观分抵消。指标需与实际原始记录一起提交，禁止先标 done 再补数据。

## 9. HTML 与 PDF

HTML 是唯一默认成品，可离线阅读、放映并在能力允许时编辑保存。资源默认内嵌；若视频导致文件过大，先向用户说明单文件成本，再按用户选择处理，不悄悄交付需要网络才能播放的文件。

PDF 是按需静态输出：一张幻灯片一页，尺寸遵循画布比例，所有内容／步骤静态可见，视频用封面，编辑器与控制条不进入打印。优先浏览器打印；自动化 PDF 功能可单独安装浏览器工具链并复用现有浏览器，不进入基本生成依赖。尽可能保留文字与链接，不能把全部页面默认截图成 PDF。检查分页、裁切、字体和透明度；有具体不支持项时明确报告。

完全移除 PPTX/PPT/ODP/Keynote 的产品入口、导出代码、转换库和 Office 发布测试。PNG 可作为开发视觉检查的临时输出，不作为默认用户成品或新兼容格式承诺。

## 10. 保留、改造、退休

|现有部分|处置|
|资料理解、来源标注、原生 Skill/NPM 接入|保留理念，改成短小 HTML 原生流程|
|IME 经验、选择交互、拖拽、对齐、媒体离页暂停、动画状态测试|按 DOM/CSS 架构评估复用；先抽掉旧 document/core 类型依赖再接入|
|PDF 打印、浏览器测量与截图设施|保留适用部分；可选工具链，不挡住普通 HTML 生成|
|Presentation IR、Recipe 槽位、强制预览收据和大事务回传|退出默认生成与新运行时；不能为了复用而留在关键路径|
|`.ppte` ZIP、CAS、journal、Portable profiles、旧版本语义迁移矩阵|退出新用户交付；历史版本在归档分支保留，不作为新版运行依赖|
|PPTX/Office 相关源码、测试、schemas、fixtures 和文档|新分发包完全移除；必要历史记录留 Git 历史|
|Host/Portable 双套编辑器|合并成同一轻量编辑 UI；直开和本地服务仅保存适配不同|

不删除用户已经生成的文件，不强制覆盖旧 HTML。旧 `.ppte` 可用保留的旧版工具打开；如用户明确需要迁移，再提供一次性离线转换工具，不把它塞入新默认包。已生成 HTML 不会因升级而自动更新。新候选走独立版本／安装目录验证后替换，当前安装不在此方案任务中改动。

## 11. 可执行阶段与停止线

H00 冻结新合同和基线 → H01 HTML 原生生成／增强 → H02 原文件保存／自动恢复 → H03 统一 UI 和日常编辑 → H04 放映／PDF → H05 旧链路退出和发布包 → H06 同模型对照验收。

第一轮可体验交付只要求：直接生成十二页好看的 HTML，打开可改标题和图片，自动写回，关闭原路径重开仍在，放映干净。**这条链没通过之前，不扩充表格高级能力、动画种类、插件或兼容格式。** 日常表格／形状／媒体能力仍在 H03/H04 逐项完成，但不能再次以功能覆盖数量替代主体验。

具体任务、依赖和检查见 [TASKS.json](TASKS.json)；远程开发按任务提交，每次同时给出一个可体验 HTML、相关代码提交和简短证据摘要。对用户依然只呈现一个作品链接，内部证据放仓库审查区。实施完成前不把本方案标为 done。

旧审查 R01–R06 的逐项承接见 [REVIEW_DISPOSITION.md](REVIEW_DISPOSITION.md)。架构改版不等于缺陷修复，未取得新实现的实际证据前，不得关闭保留的用户体验问题。

## 12. 最终必须回答的验收问题

1. 同样模型直接写 HTML 时已有的设计能力，经过 PPTe 增强后是否保留？增强前后截图能否解释每一处变化？
2. 生成是否在受控测量中接近直接 HTML 的耗时和 token，而非只测编译器毫秒数？
3. 用户是否只收到一个明确的 HTML？PDF 是否确实只在用户请求后产生？
4. 在推荐路径编辑后关掉页面，从原文件重开是否保留？断网、崩溃、只读、磁盘满、外部改动是否不丢内容？
5. 保存状态是否真实，草稿、授权、冲突是否清楚？无文件写权限时是否避免“已保存”的假象？
6. 三类对象的选择、文字格式、图片调整与表格编辑是否统一、好看、可用键盘操作？
7. 观众画面是否干净、黑屏是否真的黑、Esc 是否回到正确编辑位置？
8. 新生成包是否已经实际脱离旧核心和 Office 依赖，而不只是隐藏了菜单？
